⚔️ SQL vs NoSQL

SQL (relational) databases store data in tables with a fixed schema and relationships, queried with SQL. NoSQL ("not only SQL") is a family of different models built for different problems: documents, key-value, wide-column, graph. It is not "one thing", and it is not "better" or "worse".

Aspect SQL (PostgreSQL, MySQL) NoSQL (MongoDB, Redis, Cassandra…)
Data model Tables, rows, columns, foreign keys Documents / key-value / wide-column / graph
Schema Strict, defined up front (migrations to change) Flexible; app (or validation rules) decides
Relationships First-class: JOINs, constraints Embed or reference manually; joins are limited
Transactions Strong ACID, multi-table Varies: single-document atomic; multi-doc possible but costlier
Scaling Vertical first; read replicas; sharding is harder Many are designed for horizontal scaling
Query power Very rich ad-hoc queries, aggregations Great for known access patterns; ad-hoc can be limited
Consistency Strong by default Often tunable / eventual
Best for Finance, e-commerce, ERP, anything relational Content, catalogs, caching, real-time, huge scale, flexible data

When and where to use what

🐘 Relational (Postgres/MySQL)

Use for: users, orders, payments, inventory, bookings, reporting.

✔ ACID, joins, constraints, mature tooling, SQL skills transfer everywhere

✘ Schema changes need care; horizontal write scaling is hard

📄 Document (MongoDB)

Use for: CMS, product catalogs, user profiles, event logs, prototypes with changing shape.

✔ Flexible schema, natural JSON, easy horizontal scaling

✘ Weak at many-to-many relations; data duplication; easy to design badly

⚡ Key-value / in-memory (Redis)

Use for: cache, sessions, rate limiting, leaderboards, queues, real-time counters.

✔ Microsecond speed, rich structures, TTL

✘ RAM is costly and limited; not a primary store for complex data

🧱 Wide-column (Cassandra, ScyllaDB)

Use for: massive write-heavy time-series, messaging, IoT.

✔ Linear scalability, high availability

✘ Must design tables per query; no joins

🕸️ Graph (Neo4j)

Use for: social graphs, recommendations, fraud rings.

✔ Relationship traversal is fast and natural

✘ Niche; harder to scale; smaller ecosystem

🔎 Search (Elasticsearch, Meilisearch)

Use for: full-text search, autocomplete, log analysis.

✔ Relevance ranking, typo tolerance

✘ Not a source of truth; eventual consistency

Industry reality: most products start with PostgreSQL, add Redis for caching/sessions, and bring in MongoDB/Elasticsearch/Kafka only when a real need appears. Using several databases together is called polyglot persistence.

🥊 MySQL vs PostgreSQL

Both are excellent open-source relational databases. MySQL has historically been loved for simplicity and speed on simple reads; PostgreSQL for correctness, features and extensibility.

Feature MySQL PostgreSQL
Philosophy Simple, fast, easy to run Standards-compliant, feature-rich, extensible
SQL features Good; CTEs and window functions exist in modern versions Very advanced: full CTEs, window functions, lateral joins, many index types
JSON JSON type jsonb (binary, indexable with GIN), very strong
Data types Standard set Arrays, ranges, enums, uuid, geometric, custom types
Extensions Limited Huge ecosystem: PostGIS, pgvector, pg_trgm, TimescaleDB
Concurrency InnoDB MVCC MVCC; strong at complex concurrent workloads
Replication Mature, simple setups Streaming + logical replication
Ecosystem / hosting Everywhere, classic LAMP/WordPress world Everywhere in modern stacks (Supabase, Neon, RDS…)
Learning curve Gentle Gentle start, deeper end

Pick MySQL when…

  • You work with WordPress/legacy PHP/existing MySQL stack
  • Simple read-heavy app and team already knows it
  • Your host/tooling is built around it

Pick PostgreSQL when…

  • Starting a new project (a sensible default)
  • You want jsonb, full-text search, geo, vectors, advanced SQL
  • Data integrity and complex queries matter
Verdict for you: learn PostgreSQL deeply. The SQL you learn works 90% the same in MySQL, so you lose nothing, and Postgres is the favourite in modern full-stack and startup stacks (and pairs beautifully with Prisma).

🏗️ System design problems (explained simply)

Every problem follows the same five questions: What must it do → Which database → Data model → How it works → How it scales. Start with the 🧒 analogy, then read the details.

Interview method: 1) clarify requirements, 2) estimate size (users, reads/writes per second, storage), 3) pick data stores and justify, 4) draw the main flow, 5) find bottlenecks, 6) discuss trade-offs. Saying "it depends because…" with reasons is the right answer.
